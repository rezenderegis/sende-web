Ninguém pede um plano de recuperação de desastres até o dia em que precisa dele — e nesse dia, já é tarde para pedir. Um incêndio em um data center, um erro humano que apaga uma tabela inteira do banco de dados, um ataque de ransomware: nenhum desses cenários é raro o suficiente para ser ignorado.

Ter backup não é a mesma coisa que ter um plano de recuperação. Backup é a cópia dos dados. Recuperação é o processo testado de colocar o sistema de volta no ar a partir dessa cópia, dentro de um tempo aceitável para o negócio. Muitas empresas descobrem, só na hora da crise, que têm backups — mas ninguém nunca tentou restaurá-los, e o processo simplesmente não funciona como esperado.

<Callout type="warn" title="Pergunta que todo contrato deveria responder">
Se o banco de dados for perdido hoje, quanto tempo leva para restaurar a última cópia válida, e quantas horas ou dias de dados seriam perdidos no meio do caminho? Essas duas respostas definem seu nível real de proteção.
</Callout>

Negócios pequenos costumam achar que esse cuidado é coisa de empresa grande. Na prática, é o contrário: uma empresa grande sobrevive a uma perda de dados de alguns dias. Um negócio pequeno, dependente de um único sistema para operar, pode não sobreviver. Pedir um plano de recuperação testado — não só prometido — é uma exigência razoável em qualquer contrato de desenvolvimento.
