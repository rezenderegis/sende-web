Dívida técnica é um termo de programador, mas o conceito por trás dele é simples e qualquer dono de negócio já viveu uma versão dele: toda vez que você escolhe o caminho mais rápido em vez do caminho certo, cria um débito que precisa ser pago depois — com juros.

Em software, isso aparece como atalhos no código para cumprir um prazo apertado, funcionalidades construídas sem testar direito, ou decisões técnicas tomadas "por agora" que nunca foram revisadas. Nenhum desses atalhos é visível pra quem usa o sistema no dia seguinte. O problema aparece meses depois, quando uma mudança simples — trocar a cor de um botão, adicionar um campo — leva semanas, porque toda a base de código ficou frágil demais para ser tocada sem quebrar algo em outro lugar.

O erro de gestão mais comum é tratar dívida técnica como um problema que só interessa à equipe técnica. Na prática, ela define diretamente quanto vai custar e quanto tempo vai levar cada novidade que o negócio quiser lançar daqui para frente.

Sistemas saudáveis não têm dívida técnica zero — isso não existe em projetos reais com prazo e orçamento. Têm dívida técnica conhecida e gerenciada, com tempo reservado periodicamente para pagá-la, em vez de deixá-la se acumular até travar o desenvolvimento.
